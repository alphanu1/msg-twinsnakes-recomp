# mgso_pal.rel symbols — GGSPA4 (PAL), the engine overlay
#
# Recovered by the process in docs/decompilation-process.md. The engine is
# Konami's own code and NO PUBLIC DECOMPILATION OF IT EXISTS, so none of the
# routes that named main.dol apply here: there is no reference binary to align
# against and no upstream source to match. Everything in this file was
# established by reading the instruction stream in this binary.
#
# Format: <section> <offset> <size> <name> <origin>
#
# The same five columns as main.dol.symbols.txt so one parser reads both -
# the difference is that the number is an OFFSET here, not an address.
#
# OFFSETS ARE INTO THE REL's .text, not runtime addresses. The module loads at
# 0x7F008000 and .text begins at 0x7F0080EC, so runtime = offset + 0x7F0080EC.
# Recorded as offsets because the load address is the game's choice and has
# already changed once.
#
# TWO KINDS OF NAME LIVE HERE, AND THEY ARE NOT THE SAME CLAIM.
#
#   PascalCase / SDK spelling  — the function's ACTUAL name, where the binary
#       identifies it beyond doubt. `sqrtf` is sqrtf: frsqrte followed by
#       three Newton-Raphson rounds, leaving its ARGUMENT UNTOUCHED for
#       non-positive input, is that function and no other.
#
#       An earlier revision of this note said "returning zero for non-positive
#       input", which is wrong and was never checked against the branch. The
#       `ble` path does not touch f1, so sqrtf(-3.0f) returns -3.0f, not 0.0f.
#       Zero is merely what the case x == 0 happens to produce. The error
#       mattered: it is the one detail that distinguishes this function from
#       main.dol's `sqrt_abs` at 0x80006668, which is byte-for-byte the same
#       except that it substitutes |x| first - so a reader working from the
#       wrong note would have called them the same function.
#
#   lower_snake_case           — OUR DESCRIPTION of what the function does.
#       Konami's own identifier for it is unknown and is not being guessed at.
#       `gcn_emit_sphere_strips` is not a claim that anyone ever typed those
#       words; it is a claim about what the code does, which is checkable
#       against the disassembly and is what a name is for here.
#
# Mixing the two without marking them would be dishonest about which is
# evidence and which is a label, so the case distinction carries it.
#
# No symbol here may originate from leaked source. See project rule 9.

# --- CodeWarrior / libm ------------------------------------------------------
.text 0x017834 0x70 sqrtf own

# --- the per-frame task scheduler (see HANDOFF F94) --------------------------
# The engine's whole per-frame workload is reached through a function pointer
# in this table, which is why following `bl` targets out of the main loop
# never arrives at the renderer.
.text 0x0F394C 0xD4 gcn_task_run_all own
.text 0x0F3A20 0x38 gcn_task_link own

# --- sphere-map geometry (gcn_dgd.c / gcn_spheremap.c) -----------------------
# 32 strips of 66 vertices, position and normal per vertex, built from a
# GXBegin(GX_TRIANGLESTRIP, GX_VTXFMT2, 66) and two three-float writes to the
# write-gather pipe per vertex. The z of each normal comes from sqrtf of
# 1 - (x*x + y*y), which is what makes it a unit sphere.
.text 0x12106C 0x20C gcn_emit_sphere_strips own
.text 0x121278 0x4 gcn_gx_end own
.text 0x12127C 0x14 gcn_gx_write3f own
.text 0x121290 0x14 gcn_gx_write3f_pos own

# --- zlib, embedded in the engine ------------------------------------------
# PascalCase rule aside, these are zlib's OWN names: the binary identifies
# them beyond doubt, so they are the actual names and not a description.
#
# The evidence is the five error messages `inflate_trees_dynamic` stores into
# `z->msg`, which appear in this binary verbatim and in that order:
#
#   "oversubscribed literal/length tree"   "incomplete literal/length tree"
#   "oversubscribed distance tree"         "incomplete distance tree"
#   "empty distance tree with lengths"
#
# and the structure agrees independently: a 16-entry bit-length histogram
# (zlib's BMAX is 15), the literal/length count 0x101 = 257, the table-fill
# stride `1 << (k - w)`, and the return codes -3, -4 and -5 - Z_DATA_ERROR,
# Z_MEM_ERROR and Z_BUF_ERROR. Two routes, one answer.
#
# WHY THIS MATTERS BEYOND THE NAMES. huft_build holds 81.6% of the boot's
# samples (HANDOFF F132). The thing the boot spends its life doing is
# building Huffman tables, which is not where anyone was looking.
.text 0x0F0F2C 0x4A4 huft_build message
.text 0x0F1470 0x17C inflate_trees_dynamic message
