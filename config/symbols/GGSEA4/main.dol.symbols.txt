# Format: <section> <address> <size> <name> <origin>

# clean-room decompilation; this column is that claim's evidence, per symbol.
#
#   dtk-sig     decomp-toolkit signature match against the SDK 0x2301 build
#   mkdd-align  ordered run alignment, by consensus of three independent
#               reference decomps (mkdd, ttyd, pikmin2) that share this
#               SDK build. Where they disagreed, all claims were discarded
#   sdk2004     name confirmed against doldecomp/dolsdk2004 sources
#   sdk2004-asm full inline-assembly body matched against dolsdk2004 - the
#               strongest signature there is: the compiler emits those
#               instructions verbatim, so they are identical across SDK
#               revisions, link orders and games
#   callgraph   named by its callees and callers, weighted by rarity;
#               ambiguity refused rather than resolved by preference
#   fileline    named from the __FILE__/__LINE__ pair it hands its own
#               allocator or error routine
#   callgraph+fileline
#               both routes independently proposed the same name at the same
#               address - corroboration, and recorded as such
#   message     named from its own diagnostic message
#   ghidra      recovered by our own analysis in Ghidra
#   own         named by our own reasoning about behaviour
#   own+sdk2004 found by reading THIS binary's behaviour, then confirmed by
#               name and signature against doldecomp/dolsdk2004. The two legs
#               are independent - the behaviour is evidence from our own copy,
#               the declaration is evidence from a public clean-room source -
#               so agreement between them is corroboration, not one route
#
# NAME CASE CARRIES A CLAIM, exactly as it does in mgso_pal.rel.symbols.txt.
# A PascalCase or SDK-spelled name asserts the function's ACTUAL name. A
# lower_snake_case name is OUR DESCRIPTION of what the code does, offered
# where the real identifier is unknown and is not being guessed at. Mixing
# the two unmarked would be dishonest about which is evidence and which is
# a label, so the case distinction carries it.
#
# A NAME MAY LEGITIMATELY APPEAR TWICE. `OnReset`, `AlarmHandler` and
# `Callback` are `static` in the SDK's sources, so several translation units
# each define one and the linker keeps them all. `BootInfo` and
# `ResetFunctionInfo` are data. Do not "fix" these by deleting one - a
# uniqueness check over this file must exempt statics, and a name that IS
# unique in the SDK appearing twice is a real error. That is how
# `GXInitLightPos` at both 0x800430D8 and 0x80043358 was caught: the first
# writes the light object's `a[]` at +0x10 and is `GXInitLightAttnA`.
#
# No symbol here may originate from leaked source. See project rule 9 and
# docs/decompilation-process.md.
#
# main.dol is 7.9% of the game's code and is almost entirely SDK,
# CodeWarrior runtime and the Metrowerks TRK debugger. The engine lives
# in mgso_pal.rel. See HANDOFF.md F9.

# --- stage 5h, 2026-09-19: the memory-card module ---------------------------
# Entered through CARDGetStatus, whose body matches CARDStat.c instruction for
# instruction: the fileNo bound is CARD_MAX_FILE (0x7F), the directory stride
# is 0x40 (sizeof CARDDir), and the two memcpys are 4 bytes into CARDStat+0x28
# and 2 bytes into +0x2C - gameName and company, at exactly those offsets in
# the public header. Its three callees fell out of that and each stands on its
# own evidence, listed below. __CARDBlock's 0x220 is 2 x sizeof(CARDControl),
# and diskID at +0x10C is loaded by two of these functions.

# __CARDIsReadable HAS __CARDIsWritable INLINED INTO IT, which is why one
# 0xF4 function contains both tests. Reading only its head gives the wrong
# answer: the head is __CARDIsWritable verbatim - NOPERM, then permission
# & 0x20 with two memcmps against __CARDDiskNone - and it is the tail,
# `permission & 0x4` returning READY, that identifies the entry point. The
# call from CARDGetStatus is to __CARDIsReadable, and that agrees.

# The synchronous CARD calls are the SDK's Async-plus-__CARDSync wrapper,
# which is a shape rather than a signature: call the Async form passing
# __CARDSyncCallback, return early if it fails, otherwise block in
# __CARDSync. CARDRenameAsync is pinned by taking TWO filenames, rejecting
# a leading 0xFF or NUL in either, and returning CARD_RESULT_NAMETOOLONG
# (-12) past 32 characters - no other CARD entry point takes two names.

# --- stage 5h: three GX entry points, from the register shadows they touch --
# __GXData+0x204 is the genMode shadow and +0x1DC is PE_CONTROL (BP 0x43 -
# GXInit writes that index into its top byte at 0x8003F3EC, which is what
# fixes which register it is rather than assuming it).
#
# GXGetCullMode is the inverse of the already-named GXSetCullMode: both map
# 1 <-> 2, because the hardware's cull field has FRONT and BACK swapped
# relative to the API enum. It is adjacent to GXSetCullMode and the same
# 0x44 bytes. GXInitTexObjWrapMode sets two 2-bit fields at bits 0-1 and
# 2-3 of the texture object's mode word - wrap_s and wrap_t. GXPixModeSync
# takes no argument and re-sends PE_CONTROL unchanged, which is the whole
# of what that function is for.

# --- stage 5h: main.dol's only square root, and it is NOT sqrtf ------------
# 146 calls from the engine, the most of any unnamed function in this file.
# Body is the SDK's sqrtf exactly - frsqrte, three Newton-Raphson rounds
# against the constants 0.0, 0.5 and 3.0 at 0x800620A0/C0/C8, then frsp -
# with one addition: it first replaces its argument with |x| by clearing
# the sign bit through memory, and the iterations and the early-out both
# then run on |x|. So it returns a real root for negative input where
# sqrtf returns the input unchanged. That is a different function and is
# named for what it does, not for what it resembles. The genuine sqrtf is
# in the REL at .text 0x017834; the engine calls both, deliberately.

# --- stage 5h: three more of the matrix library -----------------------------
# All three sit in the block whose constant pool is .sdata2 0x8027E530-0x5C,
# and reading that pool out of the emitted data is what confirms them: 1.0,
# 0.0, 0.5, 2.0, -1.0, then 0.017453292 - pi/180, which only a matrix library
# keeps. Each function's constants are then exactly the ones its formula
# needs, which is a per-function check rather than a regional argument.
#
# C_MTXOrtho writes all sixteen floats of a Mtx44: 2/(r-l) and -(r+l)/(r-l),
# 2/(t-b) and -(t+b)/(t-b), -1/(f-n) and -f/(f-n), 1.0 - matching mtx.h's
# (m, t, b, l, r, n, f) argument order exactly.
#
# PSMTXQuat reads four floats as two paired singles and writes a 3x4, with
# 0.0 stored to all three translation components. It derives 2.0 as 1.0+1.0
# and 0.0 as 1.0-1.0 from a single loaded constant, which is the paired-single
# idiom throughout this library.
#
# PSVECDistance loads each vector twice at +0x0 and +0x4 so the three
# components land in two paired registers, sums the squares with ps_sum0,
# and takes one Newton-Raphson round against 0.5 and 3.0. One round, not
# three - that is PSVECMag's refinement and it distinguishes these from the
# scalar sqrt at 0x80006668.

# --- stage 5h: a set/clear pair on one flag word ---------------------------
# `bits |= 1 << n` and `bits &= ~(1 << n)` over the word at the head of the
# 0x30-byte block at .bss 0x801E7DF8. Konami's own code, so these are
# DESCRIPTIONS and lower-cased accordingly - what the block is for is not
# established, and naming it would be a guess rather than a reading. Six
# functions touch it; only these two are this simple.

# --- stage 5i, 2026-09-19: the engine's frame pipeline, named by watching it
# The first names here that were established by RUNNING the game rather than
# by reading it. The boot's stopping point (HANDOFF F122-F124) is a frame
# pipeline, and instrumenting it identified every part: a submitting side, a
# 4-slot ring, a completion callback and an idle poll thread. All Konami's
# own code, so all lower-case DESCRIPTIONS - what these are called is not
# known and is not being guessed at.
#
# The evidence for each is its observed behaviour across a whole boot, which
# is stronger than a static reading: the ring really does advance 0,1,2,3,0
# in step with 62 completions, and the flag really is the thing that decides
# whether the main loop wakes.
#
# Ring base 0x8020B918: producer index at +0x16F0, consumer at +0x16F8,
# 4 slots of 0x18, per-slot wake flag at +0x64, semaphore at +0x40.

# --- stage 5i: a correction, with the evidence that forced it --------------
# 0x8004C318 CARRIED `DEMOBeforeRender`, origin `callgraph`. It is withdrawn.
#
# Two independent reasons, neither of which was available when it was named:
#
#   1. LOCALITY. config/symbols/main.dol.files.txt attributes CR_System.c at
#      0x8004B6D8 and again at 0x8004C82C, from this binary's own __FILE__
#      strings. 0x8004C318 sits between them - Konami's code, not the SDK's
#      demo library.
#   2. BEHAVIOUR. It blocks on a semaphore, arms a slot in a 4-slot frame
#      ring, emits the frame's GX setup and advances the producer index.
#      The SDK's DEMOBeforeRender does none of that; it is a short helper
#      that sets up viewport and matrices. A function that SLEEPS is not it.
#
# The `mode` argument decides both halves together: mode == -1 skips the wait
# AND clears the slot's wake flag, so an unwaited submission also signals
# nobody. That symmetry is what ruled out "the flag was clear" as the cause
# of the boot's missing signal (F124).

# ---------------------------------------------------------------------------
# CARD, by source-order alignment against doldecomp/dolsdk2004 · sdk2004-align
#
# The method is stage 5's, applied to a different reference: dolsdk2004
# publishes the CARD sources, and the compiler emits a translation unit's
# functions in source order. Where a run of unnamed functions is BRACKETED BY
# TWO NAMED ONES and the number between matches the number the source requires
# exactly, each name is fixed by construction - there is no room for it to be
# anything else. A count that does not match means a function was stripped or
# the file order differs, and nothing in that gap is named.
#
# Three such brackets, all exact:
#
#   CARDMountAsync .. __CARDFormatRegionAsync   expects 4, found 4
#   __CARDAccess   .. __CARDIsReadable          expects 1, found 1
#   CARDGetStatus  .. CARDRenameAsync           expects 2, found 2
#
# Corroborated by shape: the SDK's sync wrappers around an async call are all
# 0x48 bytes here - CARDRename (already named) is 0x48, and so are CARDMount,
# CARDCreate and CARDSetStatus below.
#
# Gaps deliberately NOT named: __CARDFormatRegionAsync..__CARDAccess expects 4
# and has 2, and __CARDIsReadable..CreateCallbackFat expects 5 and has 4. Both
# are short by functions the linker stripped, and which one was dropped decides
# every name in the gap, so they stay unnamed.

# CARDCreate.c holds exactly three functions and the first is named, so the
# next two are its remaining two unless one was stripped - and the 0x48 sync
# wrapper being present says it was not. Anchored on one side only, which is
# why it is recorded apart from the brackets above.

# GXTransform.c, same bracket method (stage 5g).
#
#   GXLoadPosMtxImm .. GXLoadNrmMtxImm   expects 1, found 1   taken
#
# Three further GX gaps were checked and REFUSED, all short by functions the
# linker stripped:
#   GXLoadNrmMtxImm .. GXSetCurrentMtx   expects 2 (Imm3x3, Indx3x3), found 1
#   GXSetTevDirect  .. __GXUpdateBPMask  expects 5 (IndWarp..IndRepeat), found 1
#   __GXCleanGPFifo .. GXGetCPUFifo      expects 2 (Set/GetCurrentGXThread), found 1
#
# The last is tempting - 0x80040AD8 is 0x4C, far too large for a getter that
# returns one word, so it "must" be GXSetCurrentGXThread. That is resemblance,
# and resemblance is what the count test exists to refuse. It stays unnamed.

# ---- Konami's streaming sound layer, and the language index (F231, F232) ---
#
# `sd_stream_thread` is the loop the engine's `gcn_stream_serve_requests`
# wakes: it blocks in `OSReceiveMessage` on its own queue and dispatches
# seventeen commands through `jumptable_801E7C00`. `sd_stream_request_done`
# is the other half of that handshake — the engine calls it when it has
# finished serving a data request, and it posts message 1 back. Both are in
# `sd_stream2.c` by the file attribution in main.dol.files.txt.
#
# `gGameLanguage` is set from the disc's country code and, for a PAL disc,
# from `OSGetLanguage`; the engine's consumer factory refuses to create a
# stream task unless the high half of its tag equals this byte, which is how
# one language's audio is decoded and the rest discarded.
#
# Two further threads in this subsystem are identified but deliberately NOT
# named: the loops at 0x80052764 and 0x8005440C, blocking on 0x802133A4 and
# 0x80213384. What each is FOR is not established, and a name would be a
# guess dressed as a finding.

# ---- the AX frame callback, and what it drives (F233) ----------------------
#
# `AXRegisterCallback` is identified beyond doubt: `dolsdk2004`'s AXOut.c
# body is five statements — read the old pointer, disable interrupts, store
# the new one, restore, return the old — and this function is those five
# instructions in that order around the word at 0x8027DF00, which is
# therefore `__AXUserFrameCallback`. `__AXOutNewFrame` calls it through
# `blrl` when it is non-null, once per AX frame.
#
# `sd_ax_frame_callback` is what this game registers there, and
# `sd_stream_pump` is the part of it that matters to streamed media: it walks
# eight channels of stride 0x10C from 0x8021A070 and, for a channel in state
# 9, posts to the sound threads. That is the only driver of the sound
# subsystem that comes from outside it — every other sender is one sound
# thread waking another.

# ---- the voice whose position clocks the whole streamed pipeline (F234) ----
#
# `AXSetVoiceAddr` matches `dolsdk2004`'s AXVPB.c exactly: it takes the
# voice's `&p->pb.addr` (0x138 + 0x6E = 0x1A6, which is the constant this
# function adds), copies four 32-bit words from its second argument under
# `OSDisableInterrupts`, then switches on `addr->format`.
#
# The voice allocator at `0x8003198C` is left unnamed. Its behaviour is clear
# — priority, callback and user context in, a voice off the free list at
# 0x801EDF20 out — but `dolsdk2004` does not carry that function, and the
# SDK spelling would be asserted rather than confirmed.

# ---- AX's voice service, and the block the DSP owns (F235) -----------------
#
# `__AXServiceVPB` matches `dolsdk2004`'s AXVPB.c statement for statement: it
# increments a voice counter, indexes an array at `index * 0xF4` (which is
# `sizeof(AXPB)`), and on `sync == 0` copies back exactly four fields from
# the DSP's block to the user's — `state` (+0x0E), `ve.currentVolume`
# (+0x64) and `addr.currentAddress` (+0x7A/+0x7C). The array it indexes is
# therefore `__AXPB`, the block AX hands to the DSP, and the counter is
# `__AXNumVoices`, which `__AXGetNumVoices` returns in two instructions.
#
# Reading `__AXNumVoices` is what showed AX was servicing no voices at all
# before the resume mail was enabled: it read 0, and that function only ever
# increments it.
